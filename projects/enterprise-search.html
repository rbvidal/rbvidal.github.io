Enterprise Search Architecture

OpenSearchJavaDockerInformation Retrieval

The problem

Large organizations typically store information across many different systems — Confluence, SharePoint, internal wikis, shared drives, and legacy databases. Each system has its own search. Employees need to know which system contains which information before they can search. There is no single entry point.

Design approach

The architectural response is a federated search layer: a single query interface that searches across all repositories while respecting the access controls of each source system.

Connectors

Each source system gets a dedicated connector. The connector authenticates, extracts documents, normalizes metadata, and maps access control lists. Connectors run independently on their own schedules — a Confluence connector might index every 5 minutes, while a legacy database connector might run daily.

Search core

OpenSearch provides the search infrastructure. Documents are indexed with full-text fields (BM25) and optionally with vector embeddings for semantic search. Relevance tuning accounts for document type — a technical specification should rank differently than a meeting note for the same query.

Access control

Document-level permissions are indexed alongside the content. At query time, the user's identity is resolved (via LDAP or SSO), and permission filters are applied to the search. This means a search for "project budget" returns different results for a project manager than for an intern — without the search system needing to understand organizational structure.

Why incremental indexing matters

Full re-indexing is expensive and creates gaps. The connector approach uses incremental indexing — only documents changed since the last run are processed. This keeps the search index within minutes of the source system without creating load spikes. Zero-downtime reindexing is achieved by writing to a new index, then atomically swapping the alias when complete.

Observations

The hardest part is not the search technology — it is the organizational complexity. Different teams have different expectations about what "search" means. Some want a Google-like single box. Others need faceted navigation with department and document-type filters. A good architecture accommodates both without adding complexity to the search core.

The connector framework tends to become valuable beyond search — once you have a reliable pipeline that extracts and normalizes content from all internal systems, other use cases emerge: compliance auditing, automated reporting, knowledge graph construction.
